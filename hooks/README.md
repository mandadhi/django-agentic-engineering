# hooks/

There are two independent enforcement paths. They share `config/security-config.yaml` and
nothing else.

| Where the pack runs | Hooks | Files |
|---|---|---|
| The harness (`core.cli agent run`, workflows) | In-process Python callbacks registered with the Agent SDK | `agent_runtime/security_hooks.py` (not in this folder) |
| Claude Code, as the `django-engineering` plugin (Phase 4) | Claude Code command hooks | `hooks.json`, `django_pack_guard.py`, `security-policy.json` (generated), `shell_syntax.py` (generated copy, Phase 5.1) |

Projects Explorer lists every `.json` file in this folder as a hook: `hooks.json` is the plugin's
hook configuration, and `security-policy.json` is the guard's generated policy.

## Harness hooks (Phase 2; hardened in Phase 5.1)

The harness does not use `hooks.json`. Its hooks are in-process Python callbacks registered with
the Agent SDK (`ClaudeAgentOptions.hooks`) by `agent_runtime/security_hooks.py`. They run inside
the harness, can read the execution store and the approver, and are configured from
`config/security-config.yaml`. Native mechanisms come first; the hooks add only what those
mechanisms cannot express.

| `config/security-config.yaml` | Enforced by |
|---|---|
| `tools.deny`, `tools.agents[].deny` | `AgentDefinition.tools` / session `tools` = effective tools. `disallowed_tools` = the denied set. `allowed_tools` + `permission_mode="dontAsk"`. The PreToolUse hook re-checks every call. |
| `paths.deny` | Native `permissions.deny`: `Read(glob)` and `Edit(glob)`, passed through `settings`. These refuse the call *before* any hook runs (observed with CLI 2.1.317). The refusal is audited from `ResultMessage.permission_denials`. The PreToolUse hook also checks file tools and every Bash token, and confines reads and writes to the workspace and the run's artifact directory. |
| `commands.deny` | PreToolUse hook on Bash: deny. Matched against the raw command **and** every parsed simple command (nested, decoded). |
| `commands.require_approval` | PreToolUse hook on Bash: ask the configured approver (default: deny). The approver sees the complete operation and its decision is bound to that exact call. |
| `shell` (Phase 5.1) | Every Bash command is parsed (`core/shell_syntax.py`): all redirection forms, path operands, glob and brace expansions, nested shells and substitutions stay inside the workspace; deletions need approval; credential-variable expansions and environment dumps are denied. Where the platform has no OS sandbox, Bash is removed (`without_sandbox: disable`) or approval-gated. |
| `environment` (Phase 5.1) | `ClaudeAgentOptions.env`: only allow-listed variables keep their value in the CLI and its commands. |
| `secrets.patterns` + `redaction` | PostToolUse hook: `updatedToolOutput` with every string redacted and the shape unchanged. The harness logs, stored errors, result summary and inline artifacts are redacted too. |

Both hooks use `matcher=None` (every tool) and `on_failure="block"`. Any exception inside
the guard is a deny, so a hook that fails, times out or returns garbage blocks the call.
This registration is the **preventive** enforcement. `HookTripwire` (every session since Phase 5.1)
is only a **detector**: it aborts the run when a tool result arrives for a call the guard never
saw, after that call has run.
The PreToolUse hook never answers `allow`, so it can only narrow the native permissions.
Details and known limitations are in the project README, under "Security model".

## Plugin guard (Phase 4)

Outside the harness there is no execution store, approver service, artifact directory or
`settings` injection, so the plugin ships its own guard. It is **not** equivalent to the harness
hooks; the project README, "Standalone plugin security", lists the differences.

- `hooks.json` registers `django_pack_guard.py` for **PreToolUse** and **PostToolUse** on every
  tool, in exec form (`"command": "python"`, `"args": [...]`), so no shell is involved. Each hook
  has `"timeout": 30` and `"onFailure": "block"`: a crash, a timeout, or a missing `python`
  blocks the tool call (verified with Claude Code 2.1.319).
- The guard acts only on calls whose hook input `agent_type` is one of the pack's nine agents
  (`django-engineering:<id>`, or the bare id). Other agents and the main session get no opinion
  from it.
- `security-policy.json` is generated by `python -m plugin_packaging build` from
  `config/security-config.yaml`, each agent's `tools` frontmatter, the registry and
  `plugin_packaging/standalone-security.yaml`. Do not edit it; `check` and the tests fail on drift.
- The guard is standard-library Python (3.8+). A missing or unreadable policy, a missing
  `shell_syntax.py`, malformed input, an unknown agent in the plugin's namespace or any internal
  error exits with code 2, which blocks the call.
- Shell commands are parsed by `shell_syntax.py`, a byte-for-byte copy of the harness's
  `core/shell_syntax.py` written by `python -m plugin_packaging build` and compared by `check`.
  Both guards therefore analyse commands with the same code; each applies its own policy. Command
  analysis is policy, not isolation: for an OS boundary enable Claude Code's sandbox (`/sandbox`).

| Decision | When |
|---|---|
| deny | Tool not declared by the agent; globally or per-agent denied tool; denied or credential path; read outside the project and the plugin; write outside the project; any write by a read-only agent; a non-documentation write by the documentation agent; any shell use by the documentation agent; `commands.deny`; a file redirection (every form: `N>`, `&>`, `>|`, ...) or any shell command or tool not classified `read` (SEC-06: default deny, so unrecognised commands such as `make`, `pytest` or git aliases too) from a read-only agent; a shell command that cannot be analysed, lists the environment, expands a credential variable, or names a path (operand, redirection, glob or brace expansion, nested command) outside the project |
| ask | Every Write/Edit by `django-security-agent` (code changes only with your explicit approval), and every shell command or tool of it not classified `read` (SEC-06); shell commands matching `commands.require_approval` (destructive, network, history rewrite, privilege); file deletion (`rm`, `find -delete`, `find -exec rm`, ...); inline code the guard cannot analyse (`python -c`, ...) |
| allow | Only Read/Grep/Glob by a pack agent whose paths all lie inside the plugin's own `templates/`, `references/`, `skills/` or `rules/` |
| PostToolUse | Secret patterns in tool output are masked (`updatedToolOutput`), with a note asking the agent to report location and type only |
| no opinion | Everything else: Claude Code's own permissions and prompts decide |
